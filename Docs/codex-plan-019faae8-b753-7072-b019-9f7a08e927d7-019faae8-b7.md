# General File Job Proxy

## Summary

Extract the proxy into a standalone Python 3 component with no Zet imports. It will manage one strict-FIFO queue, invoke subscriber-registered workers as subprocesses, move job folders through queue states, and publish results. Zet becomes one subscriber.

## Protocol and Interfaces

- Queue layout:

```text
File_Proxy/
  Ask/<subscriber_id>/<job_id>/
  Running/<subscriber_id>/<job_id>/
  Answer/<subscriber_id>/<job_id>/
  Control/proxy.lock
```

- Subscribers publish atomically by building `.<job_id>.staging` under their `Ask/<subscriber_id>/` folder, then renaming it to `<job_id>`.
- Every ready folder contains `job.json` with:

```json
{
  "protocol_version": 1,
  "job_id": "unique-within-subscriber",
  "subscriber_id": "zet",
  "worker": "local_image",
  "created_at": "UTC ISO-8601 timestamp"
}
```

- All other inputs and application metadata are subscriber-owned files. Paths referenced by them must be relative to the job folder; reject absolute paths, traversal, and escaping symlinks.
- Local subscriber registry files map fixed worker names to argument-array commands and timeouts. Commands are never accepted from job folders.
- Invocation contract: append `--job-dir <Running/.../job_id>` to the registered command, run without a shell, and wait for completion.
- Workers write outputs only inside the job folder. Exit code `0` means success; any other exit, timeout, launch failure, or malformed job means failure. No automatic retry.
- The proxy captures stdout/stderr and writes authoritative `proxy_result.json` containing job identity, worker, status (`SUCCEEDED`, `FAILED`, or `INVALID`), timestamps, duration, exit code, and error details.
- Every completed or failed folder moves to `Answer/<subscriber_id>/<job_id>`. The subscriber removes or archives it only after successful harvesting.

## Implementation Changes

- Build a standalone package/repository containing queue models, manifest validation, filesystem transitions, registry loading, subprocess execution, singleton locking, and CLI commands: `run`, `once`, `status`, and `validate-subscriber`.
- Enforce one active proxy with an atomic runtime lock. A second instance refuses to start. If execution is interrupted, startup converts the existing `Running` job into a failed answer with `PROXY_INTERRUPTED`; it never reruns automatically.
- Select the next valid ask by `created_at`, then `subscriber_id` and `job_id`. Invalid or unknown-worker jobs become `INVALID` answers so they cannot block the queue.
- Keep status file-based and add a read-only CLI summary for queued, running, succeeded, failed, and invalid jobs, filterable by subscriber or job.
- Replace `Ollama_Proxy` with `File_Proxy`; remove the old claims, per-worker claimed folders, retry states, global dump behavior, embedded dispatch table, and compatibility readers during the coordinated cutover.
- Add a Zet backend client service for atomic publication, queue inspection, answer scanning, and harvesting from `Answer/zet`. Route all Zet LLM and automated local-image staging through it.
- Convert Zet’s Ollama and local-image implementations into subscriber-owned one-job executables. They perform only job work and output generation; the standalone proxy owns lifecycle and generic result reporting.
- Keep Zet-specific fields in its existing application manifest or payload files rather than the generic `job.json`.
- Move `manual_chatgpt_render` to a Zet-owned workflow outside the generic proxy. Preserve its FastAPI dashboard behavior without adding reusable workflow logic to `zet/web`.
- Cut over by stopping producers and workers, draining or archiving the old queue, installing the standalone proxy and Zet registry, switching Zet paths/services, then starting the new proxy. Do not accept old layouts or manifests afterward.

## Test Plan

- Validate manifests, subscriber/job identifiers, unknown workers, malformed JSON, path traversal, absolute paths, and symlink escapes.
- Verify staging folders are ignored and atomic publication never exposes partial jobs.
- Verify strict FIFO ordering and exactly one executing subprocess, including attempted concurrent proxy starts.
- Cover success, nonzero exit, launch failure, timeout, invalid output state, captured logs, and interrupted-running-job recovery.
- Verify failures always publish an answer and never retry automatically.
- Verify per-subscriber answer isolation and that one app cannot select another app’s worker registration.
- Add mock LLM and image subscribers proving the proxy is application- and payload-agnostic.
- Add Zet end-to-end tests for LLM asks, local-image asks, successful/error harvesting, application-owned answer removal, and manual-render independence.
- Run transition tests on Windows and macOS and verify atomic rename behavior on the configured Dropbox-backed queue.

## Assumptions

- Subscribers and registered worker executables are trusted local applications.
- One configured proxy host owns execution for the shared queue.
- Registry files are local deployment configuration, not writable job inputs.
- LLM and automated local-image jobs are in scope; persistent workers, HTTP APIs, priorities, automatic retries, acknowledgements, and proxy-managed retention are out of scope.
- The protocol is a clean cutover; no v1 compatibility layer is required.
